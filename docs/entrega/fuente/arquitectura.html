2. Contexto y alcance del sistema

2.1 Problema y objetivos

Problema. Quien empieza a invertir en Argentina tiene la información desparramada: el broker muestra lo que tiene pero no lo explica, los precios de los CEDEARs están en pesos y hay que pasarlos al dólar MEP a mano, las plataformas profesionales son caras y confusas, y lo que opinan otros inversores está en redes sin forma de saber si acertaron.

Objetivo general. Una aplicación web gratuita donde una persona sin formación financiera pueda seguir sus inversiones en pesos o dólares, entender el mercado, enterarse a tiempo de lo que le importa y aprender de lo que recomienda su gente, viendo cómo les fue.

ObjetivoCómo lo cumple Valeur
Saber cuánto vale lo que tengoPortfolio calculado a partir de las operaciones, con precios en vivo y conversión al dólar MEP.
Entender el mercado sin ser expertoExplorador por rubros, gráfico de velas, "Para vos" según intereses, glosario Aprendé y términos explicados en la misma pantalla.
No perderme lo importanteAlertas de precio y de variación del día (con la app abierta; y también con la app cerrada si el backend corre con la service role key, ver ADR-06), calendario de resultados y dividendos con aviso el día antes.
Aprender de otrosComunidad con recomendaciones que muestran cómo les fue desde que se dijeron, cuentas verificadas y amigos.
Cuidar los datosCada usuario ve solo lo suyo; el portfolio se comparte solo en porcentajes y solo con quien el dueño elige.

2.4 Restricciones

  • Organizativas: equipo de 3, cursada anual, trabajo académico sin presupuesto.
  • Técnicas: React + Vite en el front, Python + Flask en el backend, Supabase (Postgres + Auth) como base y autenticación, en su plan gratuito. La app se entrega para correr en la compu del docente: un ejecutable de un solo archivo (Windows y Mac) o, desde el código, un solo comando (iniciar.sh / iniciar.bat); la base y las cuentas están en la nube.
  • De datos: los precios, velas y eventos vienen de Yahoo Finance mediante la librería yfinance, gratuita, sin contrato ni garantía. Yahoo no tiene los bonos argentinos, así que el dólar MEP se calcula con los CEDEARs (ADR-07).

3. Modelo de datos

Toda la persistencia está en Postgres (Supabase). Las cuentas viven en auth.users, que administra Supabase Auth; nuestras tablas cuelgan de ahí por user_id. Las posiciones del portfolio no se guardan: se calculan a partir de trades, que es la única fuente de verdad.

6.2 Acceso a datos por Supabase

Para todo lo que es de la cuenta, el front usa supabase-js, que habla con la API REST de Supabase (https://<proyecto>.supabase.co/rest/v1) enviando el JWT de la sesión. No pasa por la API propia. Las políticas RLS de la base deciden qué puede hacer cada uno.

RecursoOperaciones que usa la appErrores posibles

watchlistselect propias · upsert · deleteSi ya lo sigue no da error: el upsert actualiza la fila. 403 (RLS).
alertsselect propias · insert · update (valor, activa) · delete400 (check), 403 (RLS).
notificationsselect propias · update read_at · delete · realtime403.

7. Vista de despliegue

Para la entrega, la app corre en la compu de quien la prueba; la base, las cuentas y los mails están en Supabase (nube). Hay dos formas de abrirla:

  • Ejecutable (Valeur-Windows.exe / Valeur-Mac.zip, en los Releases del repositorio): un solo proceso. El mismo Flask sirve la SPA ya compilada y la API en localhost:5173, y abre el navegador. No hace falta instalar nada. Lo arma GitHub Actions con PyInstaller en una máquina Windows y en una Mac, y lo prueba antes de publicarlo (ejecutable/README.md).
  • Desde el código: iniciar.sh (Mac/Linux) o iniciar.bat (Windows) crean el entorno de Python, instalan las dependencias, levantan los dos procesos (Vite y Flask) y abren el navegador. Necesita Python y Node. Es la forma de trabajar del equipo y la que muestra la figura.

Si se publicara: el front compilado (npm run build) en un hosting estático con HTTPS (Vercel, Netlify), la API en un servicio de contenedores (Render, Railway) con CORS_ORIGINS apuntando al dominio del front, y Supabase igual que ahora. El código ya está preparado: todo se configura por variables de entorno.

8. Decisiones arquitectónicas (ADR)

Cada decisión con su contexto, las alternativas, lo que elegimos y sus consecuencias. Las ADR 1 a 4 vienen de la versión anterior (actualizadas); las demás son nuevas.

ADR-01 · Cliente-servidor en capas, un monolito por lado vigente

Contexto: equipo de 3, un año de cursada. Alternativas: microservicios; serverless; monolito por capas. Decisión: una SPA y una API chica, cada una un solo desplegable. Consecuencias: desarrollo y despliegue simples, poca infraestructura; si la API creciera mucho habría que separarla.

ADR-02 · Supabase en lugar de MySQL propio vigente

Contexto: hacían falta usuarios, datos relacionales y seguridad sin presupuesto. Alternativas: MySQL local con login propio; MongoDB; Supabase. Decisión: arrancamos con MySQL y migramos a Supabase (Postgres administrado + Auth). Consecuencias: backups, autenticación y RLS listos sin mantenerlos; dependemos de un servicio externo incluso en desarrollo.

ADR-03 · Autenticación delegada en Supabase Auth reemplaza al JWT propio

Contexto: la primera versión emitía y validaba un JWT propio en Flask. Decisión: pasar todo a Supabase Auth; Flask no maneja usuarios. Consecuencias: hash bcrypt, expiración, refresh rotativo, recuperación por mail y límite de intentos sin código propio; la sesión vive en el navegador (ver el Manual Técnico).

ADR-04 · Datos de mercado con yfinance vigente

Contexto: miles de tickers con historia larga, sin presupuesto. Alternativas: APIs pagas (Alpha Vantage, IEX); yfinance. Decisión: yfinance. Consecuencias: costo cero y CEDEARs de BYMA incluidos; no es oficial y puede cambiar, lo mitigamos con errores controlados y caché.

ADR-05 · Autorización en la base con RLS, no en la API

Contexto: el front habla directo con la base. Alternativas: que todo pase por Flask y validar el dueño en cada endpoint; políticas RLS. Decisión: RLS en todas las tablas, más funciones security definer para lo que se comparte (portfolio en %, estadísticas de admin). Consecuencias: una sola regla que vale para cualquier cliente; las políticas hay que probarlas con cuidado porque un error abre datos.

ADR-06 · El backend solo da mercado; las alertas usan la service role key

Contexto: las alertas tienen que avisar aunque nadie tenga la app abierta. Alternativas: revisar solo en el navegador; un servicio aparte; un hilo en la API. Decisión: un hilo dentro de la API que cada 3 minutos lee las alertas con la service role key y escribe la notificación; la app también revisa mientras está abierta, y un "claim" condicional evita avisar dos veces. Consecuencias: un solo proceso para levantar; la clave secreta queda solo en el .env del backend. Como el ejecutable de la entrega no lleva esa clave (no se puede repartir un secreto dentro de un archivo que se descarga), ahí las alertas se revisan solo mientras Valeur está abierto; así lo explica también el Manual de usuario.

ADR-07 · Dólar MEP calculado con CEDEARs

Contexto: Yahoo no tiene AL30/GD30. Decisión: MEP = precio en pesos / precio en dólares del mismo CEDEAR (AAPL.BA / AAPLD.BA, etc.), mediana de 6 pares por día. Consecuencias: serie histórica gratis desde 2017; puede diferir unos pesos del MEP de bonos.

ADR-08 · Posiciones derivadas de las operaciones

Contexto: guardar posiciones duplicaría datos. Decisión: solo se guardan trades; posiciones, costo promedio, evolución y composición se calculan. Consecuencias: historial completo y nada que se desincronice; las reglas (no vender de más) se validan sobre toda la historia (trigger 0008).

ADR-09 · Privacidad en porcentajes

Contexto: compartir el portfolio es útil, mostrar cuánta plata tiene alguien no. Decisión: privado por defecto; amigos o todos a elección; se comparte solo peso y rendimiento. Consecuencias: la función shared_portfolio escala las cantidades para que no se puedan reconstruir montos.

ADR-10 · Entrega local: ejecutable o un comando, sin hosting

Contexto: el docente tiene que poder probarla fácil; es un trabajo escolar. Alternativas: hosting gratuito (Vercel + Render); ejecutable; script de arranque. Decisión: un ejecutable de un solo archivo para Windows y Mac (PyInstaller: el backend de Flask sirve también la SPA compilada y abre el navegador), armado y probado por GitHub Actions. Como alternativa, el repositorio con iniciar.sh / iniciar.bat. En los dos casos los datos están en Supabase, con una cuenta de prueba cargada (demo.py profe). El modo práctica quedó guardado en la rama modo-practica. Consecuencias: sin costos ni servidores que mantener, y el docente no instala nada. El ejecutable no está firmado (un certificado de desarrollador se paga), así que Windows y macOS piden confirmar la primera vez que se abre. Necesita internet para Supabase y Yahoo.

11. Glosario

TickerSímbolo de un activo (AAPL, MELI.BA, BTC-USD).
CEDEARCertificado que representa una acción del exterior y se compra en pesos en BYMA (los terminados en D, en dólares).
Dólar MEPDólar que se obtiene comprando un activo en pesos y vendiéndolo en dólares; Valeur lo usa para convertir.
Vela japonesaApertura, máximo, mínimo y cierre de un período.
Costo promedioLo que pagaste en promedio por cada unidad que tenés.
Corte de dividendoÚltimo día para tener la acción y cobrar el próximo dividendo.
SPAAplicación web de una sola página que cambia el contenido sin recargar.
API REST / endpointInterfaz HTTP entre sistemas / cada URL que responde un pedido.
JWTToken firmado que identifica al usuario en cada pedido sin guardar sesión en un servidor.
RLSRow Level Security: reglas de la base que deciden, fila por fila, quién puede leer o escribir.
Service role keyClave de Supabase que saltea el RLS; solo para procesos de confianza del servidor.
TriggerFunción de la base que se ejecuta sola ante un insert, update o delete.
Hash (bcrypt)Transformación irreversible de una contraseña, con salt, para no guardarla en texto plano.
CORSMecanismo del navegador que controla desde qué sitios se puede llamar a una API.
C4Forma de dibujar arquitectura en niveles: contexto, contenedores, componentes y código.
ADRArchitecture Decision Record: registro de una decisión, sus alternativas y consecuencias.
