1. Resumen

Valeur es una aplicación web para seguir inversiones (CEDEARs, acciones, cripto), ver el mercado y compartir recomendaciones con otros usuarios. Tiene tres piezas:

  • Front (React + Vite): todas las pantallas. Habla directo con Supabase para la cuenta y los datos del usuario.
  • Supabase (Postgres + Auth, en la nube): cuentas, contraseñas, sesiones y todas las tablas, protegidas con Row Level Security (RLS).
  • Backend propio (Python + Flask + yfinance): precios, gráficos, dólar MEP y calendario desde Yahoo Finance; además revisa las alertas de precio de todos los usuarios y deja las notificaciones.

Este manual explica cómo probamos que eso funciona (tests automáticos y pruebas manuales) y qué protege a la aplicación, separando lo que programamos nosotros de lo que nos dan Supabase y las librerías.

Números de esta entrega: 116 tests automáticos (66 en el backend con PyTest y 50 en el front con Vitest), todos pasando, más 11 casos probados sobre una base Postgres local para las reglas de la base de datos y un recorrido manual de todas las pantallas.

2. Métodos de testeo

2.1 Estrategia y niveles de prueba

Seguimos la idea de la pirámide de tests: muchas pruebas chicas y rápidas sobre la lógica (unitarias), menos pruebas sobre la comunicación entre piezas (integración) y pocas pruebas de punta a punta, que son las más lentas y frágiles.

NivelQué probamosCómo
UnitariasFunciones de negocio aisladas, sin red ni base: costo promedio y ganancia del portfolio, ventas de más, conversión pesos/dólares con el MEP, simulador "¿y si hubiera invertido?", reglas de las alertas, validación de email, usuario, contraseña y tickers, formatos de precios, exportación a CSV.PyTest (backend) y Vitest (front).
IntegraciónLos endpoints de la API: códigos de estado, forma del JSON, límites, errores, CORS y cabeceras. Yahoo Finance se reemplaza por datos falsos para que el resultado no dependa de internet.
Las reglas de la base (triggers y restricciones) se prueban corriendo las migraciones en un Postgres local.		Cliente de pruebas de Flask + PyTest.
Postgres 17 local con las migraciones 0001, 0002 y 0008.
Funcionales / E2EFlujos completos de usuario en el navegador, con datos reales: entrar, registrar operaciones, ventas inválidas, buscar, alertas, comunidad, privacidad, acceso de admin.Manual, siguiendo la matriz de casos (sección 2.4).
Elegimos que los E2E sean manuales porque la app depende de servicios externos con datos que cambian todos los días (precios de Yahoo, cuentas en Supabase). Automatizarlos implicaría simular ambos servicios enteros; con el tiempo que teníamos, preferimos cubrir bien la lógica con tests automáticos y recorrer los flujos a mano con una lista fija.

3. Medidas de seguridad

3.1 Qué delegamos en plataformas y librerías

Valeur no tiene un servidor propio de cuentas: usamos Supabase. Eso nos libera de programar a mano varias cosas difíciles de hacer bien, pero no de todo. La tabla separa qué da cada herramienta y qué sigue siendo responsabilidad nuestra.

ProveedorQué nos da de forma nativaQué nos ahorra / qué sigue siendo nuestro
Supabase AuthRegistro, inicio de sesión, hash de contraseñas con bcrypt (con salt), emisión de tokens JWT firmados con expiración, renovación con refresh token rotativo, cierre de sesión que revoca el refresh, mail de recuperación con enlace de un solo uso, límite de intentos (rate limit).No guardamos ni vemos contraseñas, no firmamos tokens ni manejamos sesiones en un servidor propio. Nuestro: reglas de contraseña en el front, mensajes de error traducidos que no filtran información, pedir la contraseña actual para cambiarla.
Supabase Postgres + PostgRESTBase administrada con backups, conexión cifrada (HTTPS/TLS) y una API REST que arma las consultas parametrizadas (no concatenamos SQL nunca). El motor de Row Level Security aplica las políticas en cada consulta.Nos protege de inyección SQL en todo el acceso a datos del front. Nuestro: escribir las políticas RLS de cada tabla, las restricciones (checks), los triggers que protegen campos sensibles y las funciones que exponen datos de otros con cuidado (sección 3.3).
ReactEscapa automáticamente todo el texto que se muestra (nombres, bios, recomendaciones), así un <script> escrito por un usuario se ve como texto y no se ejecuta.Nos protege de XSS. Nuestro: no usar dangerouslySetInnerHTML ni innerHTML (revisado: no hay ninguno en el código).
Flask-CORSAgrega las cabeceras CORS según una lista de orígenes.Nuestro: la lista (solo localhost, 127.0.0.1 y los de la variable CORS_ORIGINS).
GitHubControl de versiones y aviso de secretos subidos por error.Nuestro: .gitignore para .env, venv, node_modules y archivos compilados.
Sobre el hosting: por decisión del equipo, Valeur se entrega para correr en la compu del docente (el ejecutable de Windows o Mac, o ./iniciar.sh / iniciar.bat), no en un hosting. Por eso no contamos con protecciones de hosting como HTTPS automático para el front o mitigación de DDoS. El front y el backend corren en localhost, y todo lo que sale de la compu (Supabase y Yahoo) viaja por HTTPS.

3.2 Autenticación y manejo de sesiones

  • Mecanismo: email y contraseña con Supabase Auth. Al entrar, Supabase devuelve un access token (JWT firmado, dura 1 hora) y un refresh token. La librería supabase-js renueva el access token sola antes de que venza; cada pedido a la base lleva el JWT y Postgres sabe quién es el usuario con auth.uid().
  • Dónde se guarda: en el localStorage del navegador (es lo que hace supabase-js en una SPA). No usamos cookies HttpOnly porque no hay un servidor propio de páginas; lo compensamos con la protección contra XSS de la sección 3.1.
  • Cierre de sesión: el menú de la cuenta llama a supabase.auth.signOut(), que borra la sesión local y revoca el refresh token en Supabase; después se vuelve a /login.
  • Recuperar contraseña: /recuperar pide el email y Supabase manda un enlace de un solo uso que lleva a /nueva-clave. El mensaje es el mismo exista o no la cuenta, así no se puede averiguar qué emails están registrados.
  • Cambiar contraseña: se pide la actual y se verifica antes de aceptar la nueva.
  • Reglas de contraseña: 8 caracteres o más, se rechazan las más comunes (12345678, password, qwerty123…) y un medidor muestra qué tan fuerte es.
  • Rutas privadas: un componente Private en App.jsx envía a /login a quien no tiene sesión. Está en un solo lugar, así una pantalla nueva no queda abierta por olvidarse el chequeo. Igual, la barrera real es la base: sin sesión, la API no devuelve datos privados.

3.3 Autorización y control de acceso

La autorización está en la base de datos, no en el código del front: aunque alguien modifique la app o le pegue directo a la API con su token, Postgres aplica las mismas reglas. Todas las tablas tienen RLS activado.

TablaQuién puede qué
trades, watchlist, alertsSolo el dueño lee, crea, edita y borra sus filas (auth.uid() = user_id).
profilesLectura pública (nombre, bio, verificado); cada uno edita solo el suyo. Un trigger (protect_profile) impide que un usuario se ponga is_admin o se marque como verificado a sí mismo: esos campos solo los cambia un admin.
follows, post_likesLectura pública; cada uno crea y borra solo los suyos.
postsSe ven las públicas y las "solo amigos" si sos amigo; cada uno publica y borra las propias; el admin puede borrar cualquiera.
notificationsCada uno ve, marca como leídas y borra las suyas. Las que crean otros (seguidores, "me sirve") las insertan triggers de la base, no el front.
verification_requests, reportsCada uno ve los suyos y solo puede crearlos en estado pendiente; solo el admin ve todos y los resuelve.

Datos de otros, con cuidado. El portfolio de otra persona no se lee de trades (RLS lo impide), sino con la función shared_portfolio, que primero llama a can_see_portfolio (dueño, perfil público, o "solo amigos" y son amigos) y después devuelve solo porcentajes y cantidades escaladas, nunca montos. Las funciones de admin (admin_stats y la revisión de verificaciones y reportes) comprueban is_admin() adentro y responden error 42501 (403) a cualquier otro.

Reglas de negocio en el servidor. Además de validar en el formulario, la base rechaza operaciones con cantidad o precio no positivos, fecha futura, ventas de más y borrar una compra que respalda ventas posteriores (migración 0008, probada en 2.3).

3.4 Contraseñas y secretos

  • Contraseñas: nunca pasan por nuestro código del lado del servidor ni se guardan en nuestras tablas. Supabase las guarda con bcrypt + salt. profiles no tiene email ni contraseña.
  • Claves:
    • La anon key del front es pública por diseño: solo permite lo que dejan las políticas RLS. Por eso está en Valeur/.env.example, para que la app funcione al clonar.
    • La service role key (que saltea el RLS) vive solo en valeur-backend/.env, que no se sube al repositorio. La usa solo el proceso que revisa las alertas, y nunca llega al navegador.
  • Repositorio: .gitignore excluye .env, venv/, node_modules/, dist/ y __pycache__/. Hubo un .env del backend subido por error mientras el proyecto usaba MySQL y un login propio (de mayo a octubre de 2026). Tenía la clave de Alpha Vantage, los datos de la base MySQL local y el secreto del JWT propio; nunca tuvo la service role key de Supabase. Se sacó del repositorio, ninguna de esas claves se usa en la versión actual (MySQL y el JWT propio se reemplazaron por Supabase, ADR-02 y ADR-03 del Documento de Arquitectura) y la clave de Alpha Vantage se dio de baja en su panel.
  • Comunicación cifrada: todo lo que sale de la compu va por HTTPS/TLS (Supabase, Yahoo Finance, fuentes y logos).

3.5 Validación y sanitización de datos

DóndeQué se valida
Backend FlaskCada ticker pasa por ^[A-Z0-9.=^-]{1,15}$ antes de consultar a Yahoo (si no, 400). Los parámetros numéricos se acotan (limit entre 1 y 5000; si no es número, valor por defecto). La búsqueda se corta a 64 caracteres. /api/batch y /api/events aceptan como máximo 60 símbolos. Los valores NaN de Yahoo se descartan para no romper el JSON.
Base de datosChecks en cada tabla: formato de ticker y de usuario, side solo buy/sell, cantidad > 0, precio > 0, largo máximo de notas (200), bios (160), recomendaciones (500), valores permitidos de tipo de alerta, postura, audiencia, categoría y motivo de reporte; más los triggers de 3.3.
FrontTodos los formularios validan antes de enviar y muestran el error al lado del campo. Es para la experiencia del usuario: la seguridad no depende de esto.
Inyección SQLNo hay SQL armado con texto: el front usa supabase-js (PostgREST parametriza) y el backend no tiene SQL propio.
XSSReact escapa todo; no se usa HTML crudo.
Inyección en CSVAl exportar operaciones, un texto que empieza con = + - @ se prefija con ' para que Excel no lo ejecute como fórmula.
CORSEl backend responde con Access-Control-Allow-Origin solo a localhost, 127.0.0.1 y los orígenes de CORS_ORIGINS.

3.6 Manejo seguro de errores

  • Backend: si Yahoo Finance falla, la respuesta es 502 {"error": "Market data unavailable"}; el detalle queda solo en la consola del servidor. Las rutas inexistentes y los métodos no permitidos responden JSON (404, 405) en vez de la página HTML de Flask, y cualquier error no previsto responde 500 {"error": "Internal server error"}, sin traza.
  • Modo debug apagado: la consola interactiva de Flask (que permite ejecutar código) solo se prende con FLASK_DEBUG=1, y aun así escucha solo en la propia compu. Por defecto el servidor escucha en 127.0.0.1.
  • Front: los errores de Supabase se traducen a mensajes en castellano y sin detalles técnicos ("Email o contraseña incorrectos", "Sin conexión con el servidor. Probá de nuevo."). Las acciones que fallan muestran un aviso y no dejan la pantalla rota.
  • Cabeceras: cada respuesta del backend lleva X-Content-Type-Options: nosniff, X-Frame-Options: DENY, Referrer-Policy: no-referrer y Cache-Control: no-store.

3.7 Dependencias y configuración

  • Revisamos las dependencias del front con npm audit y actualizamos las que tenían vulnerabilidades conocidas, entre ellas react-router. Hoy npm audit no reporta vulnerabilidades.
  • La configuración va por variables de entorno (.env); los ejemplos sin secretos están en .env.example.
